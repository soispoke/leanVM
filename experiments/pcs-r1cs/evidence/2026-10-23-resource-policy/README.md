# Lane A resource policy

The parent workspace's `run-application-command.py` now defaults timed executable commands to CPUs 0 through 15 with `LEANVM_NUM_THREADS=16` and `RAYON_NUM_THREADS=16`. The native prover uses the project's own parallel pool, controlled by `LEANVM_NUM_THREADS`; both variables are set so a Rayon dependency also receives the requested limit. Yukon applies the same kernel affinity mask as `taskset -c 0-15` and records it in `machine.command_affinity`. Both thread variables are recorded in `machine.thread_environment` for every receipt.

Cargo build, check, test, Clippy, fmt and doc commands automatically use CPUs 32 through 47 with both thread settings at 16. `YUKON_COMMAND_ROLE=build` selects that mask for other gate commands. `YUKON_COMMAND_ROLE=client4` selects CPUs 0 through 3 and four threads for an optional separate client screen. These core allocations leave lane B's timed CPUs 16 through 31 independent. There is no dependency on lane B's process completion.

Build a candidate with `cargo build --locked --release -p rec_aggregation --example application_role_profile` through the wrapper, then measure its executable directly through the wrapper. The wrapper refuses `cargo run` and `cargo bench` because they combine compilation and measurement in one process affinity. Build-only benchmark targets can use `cargo build --release --benches`. A leading `env` prefix is recognized for Cargo role classification, and conflicting inline prover/thread overrides are refused. For concurrent candidate builds, use a separate candidate worktree and set `YUKON_CARGO_TARGET_DIR` to a separate target directory. Do not edit or rebuild the measured tree or its executable while its source-bound receipt is open. Running benchmarks directly avoids holding Cargo's build lock while a separate candidate builds. The existing toolchain, compiler flags, memory guards, timeout and pinned Yukon revision are unchanged.

`runner-used.py` is the exact snapshot of the parent runner used for these checks; its location-dependent `base` is the parent workspace when installed there. `plan.json` preserves the parent run plan and resource policy. The three Python probes assert actual process affinity and both effective thread variables inside the child command. The formatting check independently verifies automatic Cargo gate routing to CPUs 32 through 47. All four receipts passed with unchanged sources. These probes measure resource configuration, not application proving performance.

The earlier seven-workload quick matrix is explicitly labelled unpinned across all 64 logical CPUs with its prior 32-thread prover environment, in both its README and matrix JSON. The later application-role matched screen remains labelled CPUs 0 through 11 with 12 threads. Neither historical measurement set was rerun or relabelled as a 16-thread measurement. New workload figures use the new 16-thread policy.
