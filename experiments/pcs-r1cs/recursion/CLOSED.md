# Experimental common-key recursive relation

This document specifies the recursion layer implemented by `format_recursion::closed_recursion`. It is a tested construction conditional on the native arithmetic, Flock, bridge, WHIR and Fiat-Shamir assumptions. It is not a formal proof of their composition or an official recursion.fast submission.

Fix a BLAKE2s chain length and the context `format-closed-recursion-v1`. Let H be BLAKE2s-256. A leaf starting at a private 32-byte value x applies `x := H(0x43 || x)` for the fixed chain length, then publishes `H(0x4c || x || LE64(chain_length))`. An internal node publishes `H(0x4e || left_statement || right_statement)`. Children are ordered. The root commits to these leaf statements and their tree structure; it does not expose their starts or certify a shielded-transfer workload.

One fixed circuit has a private Boolean mode and public values `[key_lo128, key_hi128, height_u32, statement_lo128, statement_hi128]`. Hash halves follow the backend's little-endian scalar encoding. Leaf mode enforces height zero and the leaf statement. Node mode enforces both child verifiers, with the same public key, fixed metadata, context and fixed constants; it enforces `height = 1 + max(left_height, right_height)` with range-constrained 32-bit integers and no overflow, and binds the ordered node statement. All arithmetic operations and all hash I/O are constrained in both modes. Only the child verifier acceptance equations are multiplied by the Boolean mode. Dummy verifier inputs in leaf mode are not valid child proofs and need not satisfy those acceptance equations.

The trusted setup derives the verifier's metadata and constant vector by exact iteration before constructing commitments. Public capacity and hash-block capacity are padded canonically. It accepts only a stable metadata and constant vector, a satisfied canonical leaf witness and an actual setup shape equal to the derived shape. This is metadata self-description, not a hash fixed point. The key is a public circuit input; the external verifier always pins it to the actual setup key. Callers cannot authorize a replacement key by changing a certificate.

A certificate consists of a 32-bit height, a 32-byte statement and a backend proof. Its wire format is fixed-integer bincode, bounded by the backend proof cap plus 36 bytes. Decoding rejects trailing, truncated and oversized data. Decoding alone does not verify a proof. `ClosedSetup::verify` supplies the pinned key, canonical fixed public prefix and context. `prove_node` also checks its child certificates before recording them; the circuit still checks both child verifier relations.

Conditional recursive argument: assume the backend provides knowledge soundness for the fixed circuit and the transcript/hash assumptions hold for nested invocations. Extract an accepted circuit witness under the externally pinned key. Its Boolean mode yields either the base relation at height zero or two accepted child verifier relations at strictly smaller nonnegative heights. Induction on the bounded height terminates and gives the stated leaf/node semantics for a finite tree, including mixed-height children. An efficient recursive extractor, concrete security loss, and a formal proof of the native PCS/Flock composition remain open. Unit tests establish functionality and rejection cases, not this knowledge-soundness theorem.

Performance comparisons must record the whole workload, setup, proof creation (recording, child prechecks, witness preparation and proving), verification, shape and per-certificate sizes. Closure changes the old finite-tree circuit. Only optimization experiments against a frozen common-key construction can claim invariant shapes and proof sizes.

## Fixed application base relations

`ClosedSetup::from_program` extends the base relation to a fixed recorded program with two canonical 128 bit hash limbs as its public output. `prove_program` accepts a fresh witness of that exact program and produces a height zero certificate. A program obtained from `record_bound(child, application_id)` checks the complete quotient PIOP and all three PCS openings, binds the application identity and wiring key as fixed constants, and publishes the hash of the application identity and public statement using the existing little endian transcript encoding.

The common circuit contains the fixed base program and the two recursive verifiers. Base mode enforces the base program's acceptance equations and height zero. Node mode enforces the two recursive verifiers and the existing ordered statement and height equations. Both modes constrain all recorded arithmetic and hash computations. Only the base acceptance equations are multiplied by `1 + mode`; only the child acceptance equations are multiplied by `mode`. The Boolean mode equation, output canonicality and height constraints remain unconditional. The base program is therefore present during merges as well, which adds work and is a performance target.

The common key binds the fixed base program. Changing its application identity, wiring key, operation graph, public output indices or constant values changes the authorized relation and requires a new setup. This API is not a universal verifier of arbitrary application keys. A fixed base relation can describe an authorized application family, but its selector and authorization logic must themselves be constrained. Support for a mixed application family has not been established merely by accepting one workload under each separate setup.

This prototype converts an existing application proof by proving its complete recorded verifier in the common circuit. The benchmark runs this step after application proof creation, but that process placement does not determine who must pay it in a deployment. If wallets must emit the recursive certificate format, their complete proving cost includes both application proof creation and conversion. If an aggregator accepts the original application proof and converts it, conversion is aggregator work. The total always counts the step once. Direct consumption of the original application proof during a merge is the target alternative; the conversion is not assumed to be required by an Ethereum verifier.

`legacy_application_tree` preserves the original application proof and wrap-proof harness and reports application proof creation, wrap proof creation and recursive merges separately. It checks application statements against the independent workload reference, checks the wrap-proof claim against an independent byte encoding, and exercises repeated mixed height merges. The two client instances and three successive merge heights are functional observations, not repeated statistical trials. The later heights reuse the second client certificate; they do not represent a balanced tree of fresh clients. A two application proof comparison therefore counts the two creations, the two wrap proofs and only the first merge. Setup, explicit verification and serialization are separate.

Application creation in the legacy harness uses the quotient backend shared with the older application comparison, so it cannot itself supply an independent leanVM client baseline. `direct_application_vm` instead executes BLAKE2s application computations directly in leanVM, without a quotient verifier or recursive verifier. Its fixed message lengths and independently checked public statements match the corresponding circuit suite workloads. The VM uses its BLAKE2s opcode; the quotient circuit expands the application hash into full adders. These are different application arithmetizations, not evidence of an inherent VM overhead or a lower bound on R1CS proving. The direct VM control currently covers only the named BLAKE2s message workloads, not MPT, shielded transfer or hash chains.

Root certificate bytes include the 36 byte height and statement header. Quotient client certificate bytes include a 32 byte application identity, a 64 byte public statement and fixed integer bincode of the quotient proof and three openings. The direct VM control similarly includes a 32 byte program identity, the same 64 byte application statement and its serialized VM proof. Each verifier requires its trusted application setup or program. Native proof verification does not establish acceptance by the intended Ethereum verifier, EIP 8288 integration, zero knowledge or production wallet readiness.

## Native application split closure

`application_tree` now compiles the application computation into the private native arithmetic backend. It does not create a quotient application proof or record its verifier. Each input bit satisfies `b*b = b`; a full adder computes sum `x + y + c` and carry `x*y + c*(x+y)` in characteristic two. The fixed circuit wiring determines every dependency. The output hashes the fixed application identity and the four 128-bit public-statement halves. Workload instances and Boolean-circuit evaluation check those halves independently; a separate verifier process reconstructs trusted setup and expected claims and reads all five saved certificates. This is an implementation check against those references, not a proof of the application algorithms.

`SplitClosedSetup` pins a specialized base key and one node key per application relation. Height-zero certificates are native application proofs under the base key. Nodes verify height-zero children under that base key and positive-height children under the node key; every active verification equation, ordered statement binding and bounded-height equation remains enabled. Canonical setup iteration uses actual valid base certificates. Base verification and node verification do not create another application proof. Node-key preprocessing includes a canonical base proof and is reported as setup, not per-client proving.

The headline client metric is time to mempool-ready proof: witness construction plus the one native proof the wallet sends, including transport encoding. Mempool nodes verify that proof natively in a separate process, and aggregators merge it as-is with no further client work. New JSON reports `time_to_mempool_ready_proof_ms`, `mempool_proof_bytes`, `native_verification_ms` from the standalone mempool process, and `peak_client_ram_bytes` from the wallet process. Aggregator reports use `merge_time_ms` for two incoming mempool proofs and `merged_proof_bytes`. Component witness/proof/encoding times and one-time setup remain separate. The combined application_tree process labels its verification as a same-process diagnostic and its RAM as combined-process RAM; its RAM is not a peak client measurement. Historical raw receipts retain their original field names and timing boundaries. Workload fixtures, independent reference checks, trusted setup and explicit self-verification are excluded from the native wallet total. The legacy identity namespace and new `native-r1cs-full-adder-application-v1` namespace differ because these are different base proof systems.

MPT's initial native attempt failed setup. `application-native-mpt-capacity-diagnostic-t1` localized it to 26,639,333 lowered arithmetic rows (32,345,269 trace nodes), above the unchanged 2^24 native row cap. For Boolean circuits with log_rows >= 23, the new harness walks fixed dependencies backwards from public bits and omits unused sum/carry computations; every free input still receives its Boolean equation. Smaller successful matrix paths retain their original graphs. `application-native-adder-check-t2` exhaustively checks all eight three-input adder combinations, compares trimmed/untrimmed claims, verifies fresh native proofs and rejects forged non-Boolean arithmetic even after the host equality checks are made to pass. Its predecessor `-t1` incorrectly expected the prover to refuse all false witnesses; the backend can emit a rejected proof, so the corrected test checks verifier rejection. No backend cap or verifier equation was removed.

### Compatibility and shape changes

The certificate serialization and transcript domains of existing paths are unchanged. `Transcript::finish` now appends one private decoding-status input and its equality-to-one check for every symbolic transcript, including placeholders whose acceptance equations are subsequently gated. Previously it performed host-only consumption assertions. This changes recorded programs, circuit keys and potentially padded shapes/proof sizes for existing symbolic-verifier paths; old certificates are not promised to verify under newly constructed keys. Compressed/raw Merkle decoding and scalar decoding use fixed-size fallback witnesses on malformed input, keeping the operation graph independent of witness validity. Cryptographic equations still authenticate every active proof; the decoding-status input is not a replacement for them.

The private compression resource ceiling increases from 2^16 to 2^17, shared by trace allocation and bridge checks. This only changes the acceptance cap for smaller existing layouts; split node circuits may now use 131,072 padded blocks. The native arithmetic row cap remains 2^24. The new MPT output trimming changes its previously unprovable native shape to fit that existing cap. These are architecture/correctness changes, not accepted performance optimizations under an invariant-shape claim.

Poseidon BN254 and secp256k1 remain unsupported by the legacy quotient application path: the existing successful-receipt audit records their `log_rows + 5 <= quotient::domain::BASIS` capacity failure. Enlarging the quotient domain would require reviewing its field basis and opening parameters; no cheap safe repair is established here. Those failed historical receipts are preserved and have not been rerun.

### Standalone mempool verifier and current metric contract

The old path's second client proof is the wrap proof: it re-proves the application proof in the recursion format. The native split path sends one height-zero base certificate. A mempool node verifies this certificate standalone under its pinned base key, then an aggregator consumes the same certificate bytes without any additional wallet proof or wallet work. Ethereum-client format compatibility is not established. The current Rust certificate encoding and native verifier have not been shown to match an Ethereum client's expected transaction/proof envelope or verifier interface.

The exact standalone entry point is `format_recursion::private_recursion::Setup::verify(&self, outputs: &[F192], proof: &fiat_shamir::transcript::Proof) -> bool`, in `crates/format_recursion/src/private_recursion.rs`. The caller decodes the transported bytes with `format_recursion::closed_recursion::Certificate::decode`, requires height zero and equality to the externally supplied expected 32-byte application claim, and calls `pinned_base.verify(&fiat_shamir::merkle::hash_to_scalars(&statement), &certificate.proof)`. The pinned base key is `pinned_base.bridge.index.root`. The trusted `Setup` also contains the fixed public prefix, verifier metadata, index data and transcript context; a 32-byte root alone is not a complete serialized verification-key object. This trusted setup must be selected independently of the incoming certificate. The statement is the native application claim hash of the fixed application identity and its public statement, using the encoding described above, not an arbitrary claim accepted from the proof sender.

The calling sequence is:

```rust
let certificate = Certificate::decode(proof_bytes)?;
if pinned_base.bridge.index.root != pinned_base_key
    || certificate.height != 0
    || certificate.statement != expected_statement
{
    return None;
}
let words = fiat_shamir::merkle::hash_to_scalars(&expected_statement);
pinned_base.verify(&words, &certificate.proof).then_some(())
```

`format_recursion::closed_recursion::SplitClosedSetup::verify` routes height-zero certificates to exactly this base verifier and positive-height certificates to its pinned node verifier. A mempool node handling a base certificate needs only the trusted base `Setup`; it does not need node-key preprocessing, a wrap proof or a recursive merge to verify the incoming proof.

The executable entry point is the `rec_aggregation` example `application_role_profile --role mempool --workload <application> --input <certificate-file> --statement <64-hex-characters> --base-key <64-hex-characters>`. `--statement` and `--base-key` are externally supplied expected claim/key values; the binary reconstructs trusted base setup from the named fixed application and rejects a key mismatch. Its measured section decodes the certificate, checks height/statement and invokes the native base verifier. Base setup is outside that timer and no node setup or proof creation occurs in this role. Run it on CPUs 0-11 with `LEANVM_NUM_THREADS=12`, `RAYON_NUM_THREADS=12` and `CARGO_BUILD_JOBS=12`.

The six-workload reference already verifies all six wallet base certificates in separate mempool processes through this entry path, with no wrap or merge; their bytes match the independently verified saved certificates exactly. Those are standalone verification/rejection checks, not new performance comparisons. New stdout JSON carries actual CPU/thread settings. The canonical shared metric aliases are `wallet_prove_s`, `wallet_proof_bytes`, `wallet_peak_rss_kib`, `mempool_verify_ms`, `merge2to1_leaf_s`, `merged_proof_bytes` and `merge_peak_rss_kib`.
