# L4 merge investigation (in progress)

Fresh 12-thread BLAKE64 first merge on CPUs 36-47: 3.483816 s, 361,196 bytes, 9,393,676 KiB peak process RSS. Same-process diagnostic verification passed in 6.516 ms. Tracing enabled, so use as a stage diagnostic. Existing target-vm-common reference binary, source tip 0830fb9a; independent L4 rebuild underway. Raw log: `hometurf-L4/merge-profile.log`.

Archived shape and fresh setup agree: node arithmetic log_rows=22, block_log=16, n_blocks=65536, connector_start=2097152, q_offset=50331648, stack_log=26. Twelve arithmetic F64 limb columns contain 50,331,648 words. Hash packed witness adds 2^(14-6+16)=16,777,216 words. Total joint witness is exactly 67,108,864 words, before rate expansion and fixed index commitment. The 361 KB certificate size is not the committed prover data size.

This report is chronological; the later native-hash census, ABAB, declined-rate decision, node screen and corrected analytic appendix supersede the early provisional estimates. Reusable first/tree-key closure and two-child index-claim batching remain incomplete.

## Stage breakdown and causal diagnosis

The trace tree for the fresh run reports: record node witness 139 ms, compile witness 123 ms, arithmetic witness 262 ms, hash witness 54.9 ms, joint commitment 747 ms, arithmetic reduction 608 ms, hash reduction 392 ms, joint opening 581 ms, and index opening 288 ms. These sum to approximately 3.19 s; the remainder is parallel scheduling, transcript, child admission, and tracing overhead. The archived independent run is 3.387 s, so tracing is a small perturbation, not the explanation for the multi-second result.

The node shape is `log_rows=22`, hence 4,194,304 padded arithmetic rows. The fixed native circuit has 12 populated F64 limbs per row (four F192 values represented by three F64 limbs), or 50,331,648 committed F64 words. The 65,536 BLAKE2s compression slots each use `2^14` packed z slots and six-bit packing, adding 16,777,216 words. Thus the joint witness is 67,108,864 F64 words before opening-rate expansion and the separately committed index. The two child Merkle paths and transcript are represented by the 65,536 scheduled compression blocks; their hash rows are therefore 65,536 compression rows at the block level, with 16,384 packed field slots per block. Copy/connector rows are included in the padded arithmetic circuit; the exact unpadded count is not exported by the current profiler, so it would be unsound to claim a finer row census.

This makes the dominant cause clear. It is not the 361 KB transported proof: proving commits and opens tens of millions of field words. It is not simply the 112 L0 queries at rate 1/4: those queries affect opening work, but the commitment, arithmetic reduction, hash reduction, and two openings already account for 2.33 s. The node's 2^22 padding and 65,536 hash schedule force a large fixed witness even when the children are only 64-byte applications. The two-proof structure (joint private witness plus index opening) adds the 581 ms joint and 288 ms index openings. LeanVM's first-level node is reported at 0.52–0.59 s at 12 threads, with approximately 9.57M committed words for the wrapped leaf and 5.08M for wrap-only; its lower table size and RISC-V cycle execution explain the 6–7x gap. Proof-byte size is not predictive.

## One-proof cost inside recursion

A single native R1CS base certificate is 247,956 bytes for BLAKE2s-64B and standalone decode plus verification is 5.2–7.0 ms in the separate-process matrix. The verifier's trusted shape is the base shape (`log_rows=17`, 131,072 rows, 39 compression blocks), while a recursive node uses the padded 2^22 shape above. A recursion machine that verifies one R1CS proof must execute the transcript and Merkle checks over the certificate, then the arithmetic and opening verifier. A conservative accounting is one hash row per committed Merkle/transcript compression plus one F192 multiplication for each recorded extension-field product in the verifier. The later first-only census exports 214,302 F192 Mul nodes for two children and 20,132 hash compressions including outer assembly; earlier counters were unavailable; the shape implies at least O(log rows) Fiat-Shamir rounds and O(112) L0 query paths. This is qualitatively much smaller than proving the node, but materially larger than verifying one leanVM proof, whose wrapping benchmark is about 9.57M committed words per leaf (5.08M wrap-only) and whose verifier is already expressed as VM execution.

## Levers

* Reduce node padding by admitting a smaller trusted node shape. At fixed workload this removes roughly 4,194,304-row arithmetic work and 50.3M words, potentially saving the 0.61 s arithmetic reduction and part of commitment/opening. This requires a new fixed key and rejection tests; it is the highest-value safe lever.
* Batch child Merkle/transcript queries before hashing. This can reduce repeated hash witness and hash reduction work (392 ms observed), with no soundness change if every original query remains bound. Expected saving is bounded by that 392 ms stage.
* Raise the leaf opening rate (lower inverse rate) only after re-deriving PCS soundness parameters. It can reduce query/opening volume, but changes proof length and security accounting; no safe numeric saving is claimed here.
* Remove neither child nor transcript checks. The two-proof structure could be fused only with a new soundness proof; it is not a safe quick optimization.

## Analytic row model (conditional, no lookup implementation)

Use separate units: a Boolean full-adder gate, a native F192 row, a lookup request, and a committed F64 word are not interchangeable. Let `w(C)` be committed words per RISC-V cycle at workload scale C. It includes table-specific power-of-two padding and hash witness allocation, so it is not constant across apps. Cost is `cycles * w(C)`, with the complete table census preferred to any scalar approximation. A 32-bit word lookup is not a practical one-row table: a two-input lookup has 2^64 entries. Assume instead 8-bit limbs with a shared 2^16-entry XOR/AND table and explicit range checks.

| operation | bit-level constraints | word/8-bit-lookup model | RV64IM instructions before control/memory |
|---|---|---|---|
| 32-bit add | 32 full adders; carry-out may be discarded | 4 byte add/carry lookups, plus range checks unless fused | 1 addw |
| 32-bit XOR | 32 XOR gates | 4 byte XOR lookups | 1 xor, plus truncation if needed |
| constant rotate | free wire permutation, not 32 arithmetic gates | byte-aligned rotate free wiring; otherwise bit-split/recombine checks | shift, shift, or (3 instructions) |
| multiply modulo q | schoolbook O(b^2) Boolean work plus reduction | limb products plus quotient/remainder relation and bounded carries; field-dependent, not one F192 multiplication | multiply plus reduction sequence; no single RV64IM mod-q instruction |
| SHA-256 compression | ~20k-40k Boolean gates (implementation-dependent) | schedule: 96 XOR + 192 rotates/shifts + 144 adds; rounds: 448 XOR + 384 rotates + 320 AND + ~448 adds; four byte lookups per binary word operation, plus range/carry checks | same operation counts translated to instructions, with 3 instructions/rotate and load/store overhead |
| Keccak-f[1600] | per round: theta 320 XOR bits, D 320 XOR, state mixing 1600 XOR, chi 1600 AND +1600 XOR; 24 rounds; rotations free | per round 76 word XORs for theta/mixing, 25 AND +25 XOR for chi on 64-bit lanes; 8 byte lookups per lane binary op, rotations need bit alignment checks | 24 times lane XOR/AND operations plus rotates (3 instructions each), loads/stores |

SHA256 of 1 KiB requires 17 compression blocks including standard padding, hence 17 times the compression model. Keccak-256 uses a 136-byte rate and exactly eight permutations for a 1 KiB message including padding. For MPT use the sum over actual encoded node lengths of `ceil((length+1)/136)` Keccak permutations, plus RLP/path checks; a trie depth alone does not determine cost. Falcon needs separate counts for NTT butterflies, modular products, coefficient range checks and SHAKE permutations; q=12289 arithmetic cannot be represented by a free characteristic-two field product. Lookup savings are plausible for bytewise hashes and bounded coefficients but require a lookup argument, table commitment/amortization and sound range constraints. No lookup backend or measured break-even point is established here. R1CS matches leanVM only when its padded committed-word total and per-word proving time approach the VM's, not merely when abstract gate counts are smaller.

## Exact verifier census and right-sizing screen

A release census of the fixed BLAKE64 split-node program reports 63,426 BLAKE2s compression calls, 2,034,321 pre-bridge arithmetic rows, and 133,479 arithmetic checks. The operation census is: Add 708,413; Mul 589,175; Select 101,977; Slice 154,235; Hash 32,661; HashHigh 32,661; Pack 12,729; Input 131,251; Constant 989. The 65,536 hash slots are therefore the exact next power of two above the real compression need, with only 2,110 unused slots.

The requested query expression (112+45+28+21+16) is 222 L0 queries per child family before path depth and transcript openings. The measured 63,426 compression calls include both children, all Merkle path and transcript compression work, verifier opening reductions, and the fixed bridge schedule. The source records both base and node verifier shapes for each child, then gates the relevant checks by child height, so the first merge still carries the universal either-kind verifier circuit. This is why simply counting application Merkle queries underestimates the circuit.

The bridge connector schedule adds `6 * 65,536 = 393,216` rows. Together with the 2,034,321 pre-bridge rows and alignment, this crosses the 2^21 boundary and forces `log_rows=22` (2^22 rows). A right-sized node would need fewer than 32,768 compression slots, or a different connector representation, to reach 2^21 rows. The current exact 63,426-call universal verifier cannot meet that bound by changing a constant: 65,536 is already minimal under the current fixed-point program. Shrinking below it requires reducing verifier work (native child proof hash rows, query batching, or a redesigned shared base/node verifier) while retaining both child-kind checks.

No shape-changing candidate was screened because the available branch has the old bit-level base verifier and its measured lower bound is 63,426 compressions. Applying a smaller `n_blocks` would reject valid witnesses or truncate compression commitments, so it would weaken soundness and was not attempted. The safe screen result is therefore a negative result: current constants are already right-sized for the measured program, while the 2^22 padding follows from the universal verifier's connector schedule.

## Shared subtree lever

The current R1CS verifier loops over each query and hashes every path independently. LeanVM's `authenticate` groups queries into strata, hashes each low path once, then hashes shared upper-subtree parents once and ties repeated nodes with copy equalities. The R1CS BLAKE64 base schedule has 112 depth-17 queries, plus opening groups of 45/28/23/20/56/32 queries at depths 16/15/15/14/17/16. A shared-subtree implementation would retain every leaf and sibling binding but replace duplicate upper path hashes with one HASH row and copy links. Exact savings depend on the sampled query prefixes and are not measurable without changing the recorder; the ceiling is the path-hash portion of the 14,598 native-hash compression schedule. No unreviewed verifier change was made.

The remaining first-level arithmetic is 578,847 rows after native hash rows, so reaching 2^19 (524,288) requires removing at least 54,559 rows, about 9.4%. Shared upper-subtree hashing can plausibly remove that many hash/Select/Slice rows only if query prefixes overlap substantially; it must be measured with an ABAB circuit and rejection tests before acceptance. Lowering the leaf opening rate is report-only here because it shifts query and commitment cost to wallet proofs and changes PCS/security accounting.

## Shared-top-parent ABAB screen (rejected)

The current R1CS queries are independent bit slices from transcript samples (`Transcript::queries`), unlike leanVM's stratified queries. Directly substituting leanVM's strata would change the query distribution/protocol. Instead the screen hashes the root parent once, then ties every later query's top left/right pair to the first pair, including every supplied top sibling. It retains all original authentication checks through equalities and does not change query indices.

ABAB plain/shared-top timings are 0.927824913, 0.945546161, 0.957316914, 0.949007953 s. Compression count falls 14,598 to 14,062 and pre-bridge rows 578,847 to 577,775; committed words stay 16,777,216. Candidate proof bytes are 324,232 versus 323,976. Seven verifier tests pass with sharing enabled, including repeated-query wrong-top-sibling rejection and the existing range, omitted-zero-lane, public/context/key binding checks. The patch is archived as `artifacts/L4-shared-top-rejected.patch` and removed from the active verifier because the timing is mixed and no padding threshold is crossed. This is a negative screen, not an accepted optimization. Sharing larger subtrees with independent queries needs more selector/advice constraints; the largest-group coverage guarantee used by leanVM does not hold here.

## Add reuse screen (rejected)

The existing four-cell relation is `z=x*y+u`; a materialized linear add costs a row `z=x*1+u`. Exact commutative add common-subexpression reuse saves 5,088 rows (578,847 to 573,759; linear-add bucket 146,472 to 141,384), but leaves 14,598 compressions and 16,777,216 committed words unchanged. ABAB plain/reuse times are 0.925761904, 0.983086308, 0.922761913, 1.021522561 s. All harness verification/rejection assertions pass. It is slower and crosses no padding threshold, so the patch is rejected and removed.

General affine folding requires authenticating sparse linear forms in the row/index relation. The current multiply-add fusion can remove only a single-use product feeding one addition. An arbitrary add chain cannot be substituted into a four-cell multiplication without extra constraints or a different gate. A wide-linear-row candidate would change the fixed circuit index, copy argument and verifier arithmetic. No such soundness-relevant row-format change was made, and no completed wide-row speedup is claimed.

## Two-child claim batching status

Same-circuit children share the fixed index root, while their witness roots, Fiat-Shamir transcripts and evaluation points differ. The existing `opening_rate` already combines the claims within each child's index opening. A node-level opening can in principle batch both vectors under that shared index root with a fresh challenge bound to both child transcripts and all claims. It must use the public index prover data to create an additional aggregate opening and replace the separately recorded child index-opening checks, while preserving the earlier reductions, complete witness openings and statement binding. This is implementable protocol work, not an impossibility result. It has not been implemented or timed here. Batching Flock reductions is more involved because their witness commitments differ; combining terminal equations alone does not authenticate both witnesses.

## Sparse-affine candidate status

The measured algebraic census contains 146,472 plain linear-add rows in the complete native-hash first-merge circuit, not 196,394. Stage-attributed Add operations can emit multiplication rows through fusion and must not be counted as plain linear rows. Deleting all 146,472 plain add rows, even optimistically, leaves 432,375 pre-bridge rows, already above the 425,472-program-row threshold after accounting for the 512-word public prefix. General affine folding also affects multiplication operands, copy constraints and hash-port materialization, so this subtraction is not a completed affine census.

A valid measurement prototype must expand add chains into canonical sparse coefficient maps, count the surviving nonlinear constraints and materialized hash/range/public ports, count sparse nonzeros and their index/copy costs, and repeat for the shielded wallet. No such prototype has run yet. Previous 382,453-row/14.68M-word estimates were withdrawn: they mixed operation and emitted-row counts and used the wrong hash-witness size. At unchanged 16,384 hash slots, the packed hash witness is 4,194,304 F64 words. A hypothetical 2^19 arithmetic table would occupy 6,291,456 words, but joint layout aligns that prefix to the hash table's 4,194,304-word boundary, giving 12,582,912 total words before coding. This conditional shape saves 25% versus 16,777,216 words; it is not an achieved candidate.

A sparse affine format changes the committed index relation, coefficient authentication and copy argument. A review must establish canonical sparse encoding, coefficient/key binding, zero omission and padding, equivalent nonlinear equations, authenticated materialized hash ports, and Fiat-Shamir binding of new commitments. No soundness claim or measured affine speedup is made.

## Fixed-shape arithmetic reuse audit after rate diagnostics

The Flock matrix walk is fixed in topology, but its field values depend on each child's independent Fiat-Shamir challenges. In `flock_trace::reduce`, the Lagrange weights depend on each child's sampled z, the eq kernel on each child's sampled point, and the matrix bilinear walk on those dynamic vectors. Same circuit/key does not make those values equal across children. Constant-only operations already fold in `S::Add`/`S::Mul`; `S::c` interns constants, and private hash lowering folds fixed prefixes. Thus sharing the evaluated Lagrange/eq vectors across children would remove a required dependence on one child's transcript. The prior commutative-add reuse screen saved only 5,088 rows and regressed, so it remains rejected. Further four-cell savings need an algebraic refactor of the dynamic matrix walk with equality tests against the existing bilinear reference, rather than precomputing child-dependent values as constants. No such refactor or new 2^19 claim is established here.

## Completion audit and corrected analytic model

The latest closure regression run passed all six tests, including direct malformed-child rejection and repeated composition with wrong-claim rejection. The final node diagnostic also checks a changed child statement before proving and rejects it as an unsatisfied trace. The node screen remains a separate second-level setup, so it is evidence about node cost, not evidence that a single reusable first/tree key has been implemented.

The RISC-V comparison should use the matched per-claim recursion tables from L2 rather than the older hashchain table: SHA-256 1 KiB uses 60,119 rows and 5,358,592 committed words (EMUL 38,186, EXK 12,425, HASH 5,508, SPLIT 271, CAST 3,234, PUB 495); Keccak-256 1 KiB uses 59,633 rows and the same 5,358,592 words (EMUL 37,264, EXK 13,077, HASH 5,358, SPLIT 265, CAST 3,183, PUB 486). These are arity-one recursion circuits, not two-child merge circuits.

The following explicit counts supersede the earlier rough analytic table. They count a particular straight-line implementation, not optimized circuit lower bounds. Let X32/A32/B32 denote 32-bit XOR/add/AND and R32/S32 denote constant rotate/shift. Use `Ch(e,f,g)=g XOR (e AND (f XOR g))` and `Maj(a,b,c)=(a AND b) XOR (c AND (a XOR b))`. One SHA-256 compression then uses 704 X32, 192 B32, 600 A32, 576 R32, and 96 S32: 48 schedule words contribute 192 XOR, 144 adds, 192 rotates and 96 shifts; 64 rounds contribute 512 XOR, 192 AND, 448 adds and 384 rotates; feed-forward contributes eight adds. Rotates/shifts are wiring in a bit circuit. A modulo-2^32 ripple adder can use 93 two-input XOR and 61 AND gates (discard the final carry). This gives 121,072 Boolean XOR/AND gates per compression for this explicit construction, before constant propagation, input bit checks and copy constraints. Four byte requests per XOR/AND/add give 5,984 requests per compression before rotate splitting, carry/range checks and lookup argument overhead. These are requests, not four-cell rows.

For Keccak-f use theta's 20 column XORs, five D XORs and 25 state XORs, and chi as `a XOR c XOR (b AND c)` with the complemented-b term expanded in characteristic two. Each round has 100 lane XORs, 25 lane ANDs and one XOR of the iota constant, plus five theta rotates and 24 nonzero rho rotations. Thus an upper operation count is 2,424 64-bit XORs, 600 64-bit ANDs and 696 constant rotates per permutation. This is 193,536 Boolean XOR/AND gates, or 24,192 byte XOR/AND requests before rotate splitting and lookup overhead. The iota-constant XOR and constant propagation can reduce both counts. This is a deliberately explicit uniform count, not a claim that iota needs a lookup or that every bit/byte operation emits a row.

SHA-256 of 1 KiB uses 17 padded compression blocks: 2,058,224 Boolean gates or 101,728 byte requests under the construction above. Keccak-256 of 1 KiB uses eight permutations: 1,548,288 Boolean gates or 193,536 byte requests under the uniform model. On RV64IM, a rotate uses shifts plus OR (three instructions); the SHA core above has a 3,320-instruction arithmetic/bitwise budget per compression, or 56,440 for 17 blocks, before loads/stores, loops, 32-bit canonicalization and padding. The Keccak core has 5,112 operations/instructions per permutation including three instructions per rotate, or 40,896 for eight permutations before loads/stores and control. Neither figure is a measured cycle count. Committed words must be computed from actual padded execution tables and bus/lookup multiplicities; multiplying these instruction counts by the entire 5.36M-word recursive proof would be invalid.

For MPT, let encoded node lengths be L_i. The Keccak part uses `sum_i (floor(L_i/136)+1)` permutations, plus key hashing if required by the statement; append RLP canonicality, child-reference equality, nibble-path and branching checks. A trie depth alone does not determine either bytes or rows. For Falcon-512, each 512-point radix-two NTT has `(512/2)*9 = 2,304` butterflies. Two forward transforms plus one inverse therefore have 6,912 twiddle multiplications and 13,824 butterfly additions/subtractions, plus 512 pointwise products, final scaling/centering, coefficient decode/ranges and norm checks. The inspected RV implementation uses Plantard products for twiddles and Montgomery pointwise products. Hash-to-point uses SHAKE256 and rejection sampling: a 32-byte message plus 40-byte nonce fits the first absorption block; 512 accepted 16-bit samples require at least eight 136-byte squeeze blocks and about nine on average, with no fixed maximum without a protocol cap. Budget the Keccak work by actual squeeze blocks, not by treating 512 modular products as the complete verifier. A lookup circuit must prove bounded integer products and quotient/remainder carries modulo 12289; characteristic-two multiplication alone is not that relation.

R1CS with lookups could approach leanVM when Boolean/byte operations dominate and shared lookup tables amortize across many requests. That is conditional on authenticating table membership, addresses, carries, ranges and materialized ports, and on crossing actual commitment padding thresholds. The current four-cell native backend has no such lookup implementation, so none of these request counts establishes measured parity or soundness. L2 owns the true R1CS/CCS format screen; this is only an analytic application model.

For the recursion-machine translation estimate, one old bit-level BLAKE64 base verifier in the native backend contributes 10,065 hash compressions and 107,151 recorded F192 products. A direct VM encoding therefore needs at least about 10,065 HASH rows and 107,151 extension products, plus CAST/SPLIT/EXK and copy-bus rows. This estimate is independent of the 5.36M-word per-claim leanVM recursion table and is not a measured R1CS verifier guest.
